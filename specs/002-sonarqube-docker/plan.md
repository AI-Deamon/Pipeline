# Implementation Plan: SonarQube Docker Container

**Branch**: `002-sonarqube-docker` | **Date**: 2026-05-26 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-sonarqube-docker/spec.md`

## Summary

Add SonarQube as a Docker container in the project's Docker Compose stack, integrated with the shared PostgreSQL instance for storage and exposed on the host network for Jenkins pipeline connectivity and operator access. Replace the current host-installed SonarQube dependency with a fully containerized, restart-persistent service. Update authentication tokens across all configuration locations.

## Technical Context

**Language/Version**: Docker Compose v2, SonarQube LTS Community Edition, PostgreSQL 16

**Primary Dependencies**: `sonarqube:lts-community` Docker image, shared PostgreSQL service, `network_mode: host`

**Storage**: SonarQube data volumes (`sonarqube_data`, `sonarqube_extensions`, `sonarqube_logs`) on the Docker host + dedicated `sonarqube` database in shared PostgreSQL

**Testing**: Manual verification — start stack, verify `http://localhost:9000` responds, trigger a Jenkins scan and confirm `sonar_scanner` stage connects successfully, verify backend `fetch_sonar_issues()` returns results

**Target Platform**: Linux server, Docker Compose with host networking (matching existing pattern)

**Project Type**: Web application (DevSecOps platform) with Docker Compose infrastructure changes

**Performance Goals**: SonarQube container healthy and accepting connections within 3 minutes of stack start; backend issue fetch under 30 seconds

**Constraints**: Port 9000 must not be in use on the host (conflict if legacy SonarQube still running); SonarQube embedded Elasticsearch requires `vm.max_map_count` kernel parameter or bootstrap check disable; shared PostgreSQL needs a dedicated database created before SonarQube first start

**Scale/Scope**: Single-instance SonarQube Community Edition, single-tenant deployment
